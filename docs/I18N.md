# KCS three-language maintenance

KCS supports `en`, `ms`, and `zh`. English is the canonical fallback language.

## Translation keys

- Use stable module keys: `account.*`, `customer.*`, `branch.*`, `material.*`, `employee.*`, `vehicle.*`, `dispatch.*`, `specialRequest.*`, `zone.*`, `gps.*`, `import.*`, `schedule.*`, `common.*`, and `apiError.*`.
- Never use an English, Chinese, or Bahasa Melayu sentence as a translation key.
- Add every new key to all three language objects in `src/translations.js`.
- `translate()` falls back to English. Development builds warn when a selected-language key is missing.
- A source-alias compatibility map localises older static labels while pages move to direct `t(key)` calls. Database values are not aliases and remain unchanged.

## API errors

The server returns a stable `errorCode`. `src/apiClient.js` maps it to `apiError.*` using the active account language. Unknown failures use `apiError.generic`; stack traces, SQL and local paths are not shown to ordinary users. HTTP status and transaction behaviour are unchanged.

## Addresses and official place names

Customer/Branch addresses, Area names, Operational Location names and Zone Group names are canonical business data and are never translated. New or edited values must use English or Bahasa Melayu; CJK characters are rejected with `INVALID_LOCATION_TEXT`.

New-database initialization uses:

- Kuching A — BDC
- Kuching B — Matang
- Serian A
- Serian B — Penrissen
- Samarahan A
- Samarahan B
- Lundu / Bau

Existing v19 databases are not modified. Production Zone names and legacy addresses containing Chinese require a separate, backed-up and audited data-correction operation.

## Testing

Run `npm run lint`, `npm run build`, `npm test`, and `git diff --check`. `test/i18nV19.test.mjs` verifies key parity, route-surface text, Zone Rename Modal behavior contracts, API error codes, unchanged place values, CJK rejection, retired prototype removal and 390×844 responsive protection.

`test/i18nRender.test.mjs` loads the real JSX modules through Vite SSR and renders them with React/JSDOM. It exercises Customer Branch, GPS Collector, Buyer, Operational Location and Excel/CSV Import & Export in English and Bahasa Melayu, plus the initial surface of every production route. A separate source gate scans all production `.js` and `.jsx` files and reports every hard-coded CJK match with file, line and source text.

When a production acceptance test finds a literal missed by key-only coverage, add a stable module key in all three languages and add the visible source phrase to the route-surface matrix. Dynamic Customer, Branch, address, Area, Operational Location and Zone values must use `data-i18n-raw`; they are data, not interface translations.
